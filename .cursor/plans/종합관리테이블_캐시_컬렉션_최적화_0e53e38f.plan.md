# 종합관리테이블 캐시 컬렉션 최적화 계획

## 현재 문제점

- `useProducts` 훅이 매번 `packaging-reports`와 `quality-inspections` 컬렉션에서 최대 2000개씩 문서를 조회
- 클라이언트 사이드에서 복잡한 집계 로직 실행 (제품 중복 제거, 최신 정보 추출, 평균 계산)
- 실시간 구독으로 인해 데이터 변경 시마다 전체 재계산으로 인한 성능 저하

## 해결 방안

별도의 `product-summary` 컬렉션을 생성하여 사전 집계된 데이터를 저장하고, 원본 데이터 변경 시 Cloud Functions가 자동으로 캐시를 업데이트합니다.

## 구현 단계

### 1. 캐시 컬렉션 구조 설계

**파일**: `docs/product-summary-collection-structure.md` (새로 생성)

`product-summary` 컬렉션 구조:

- 문서 ID: `{supplier}_{productName}_{partName}_{specification}` (기존 `generateProductId`와 동일)
- 필드:
  - `id`: 제품 고유 ID
  - `supplier`, `productName`, `partName`, `specification`: 기본 정보
  - `latestJig`: 최신 사용지그
  - `latestJigDate`: 최신 지그 정보 날짜
  - `latestUndercoatData`: 최신 하도데이터
  - `latestTopcoatData`: 최신 상도데이터
  - `averagePersonnelCount`: 평균작업인원
  - `latestLineRatio`: 최근 비율(스핀들비율)
  - `averageRPM`: 평균 작업속도(RPM)
  - `lastUpdated`: 마지막 업데이트 시간
  - `sourceReportIds`: 참조하는 packaging-reports 문서 ID 배열
  - `sourceInspectionIds`: 참조하는 quality-inspections 문서 ID 배열

### 2. Cloud Functions 구현

**파일**: `functions/src/index.ts` (새로 생성 또는 기존 파일 수정)


#### 2.2 quality-inspections 변경 트리거

#### 2.3 캐시 업데이트 로직

**파일**: `functions/src/services/productSummaryService.ts` (새로 생성)

- 기존 `productService.ts`의 `getProducts` 로직을 서버 사이드로 이동
- 영향받는 제품 ID 목록 계산
- 각 제품별로 `product-summary` 문서 업데이트 또는 생성
- 배치 처리로 여러 제품 동시 업데이트

- 쓰기: Cloud Functions만 허용 (클라이언트 직접 쓰기 금지)

## 성능 개선 효과

### 현재 방식

- 조회: packaging-reports 2000개 + quality-inspections 2000개 = 4000개 문서
- 처리: 클라이언트 사이드 집계 (복잡한 로직)
- 예상 시간: 2-5초

### 캐시 방식

- 조회: product-summary 컬렉션만 조회 (제품 수만큼, 보통 100-500개)
- 처리: 서버 사이드에서 사전 집계 완료
- 예상 시간: 0.5-1초

## 추가 개선 방안

### 1. 증분 업데이트 최적화

**목적**: 전체 재계산 대신 변경된 제품만 업데이트

**구현**:

- Cloud Functions에서 변경된 report/inspection의 제품 ID만 추출
- 해당 제품의 `product-summary`만 재계산
- 배치 처리로 여러 제품 동시 업데이트 (최대 500개)

**효과**: 업데이트 시간 90% 감소 (전체 재계산: 10초 → 증분 업데이트: 1초)

### 2. 배치 처리 및 Debouncing

**목적**: 짧은 시간 내 여러 변경사항을 모아서 한 번에 처리

**구현**:

- Cloud Functions에서 Pub/Sub를 사용한 배치 큐
- 5초 내 변경사항을 모아서 한 번에 처리
- 중복 제거 (같은 제품이 여러 번 변경되면 마지막 것만 처리)

**효과**: Cloud Functions 호출 횟수 80% 감소

### 3. 필드 선택적 조회 (Field Selection)

**목적**: 필요한 필드만 조회하여 네트워크 비용 감소

**구현**:

```typescript
// 기존: 전체 문서 조회
const snapshot = await getDocs(collection(db, 'product-summary'));

// 개선: 필요한 필드만 조회
const snapshot = await getDocs(
  query(
    collection(db, 'product-summary'),
    select('id', 'supplier', 'productName', 'partName', 'specification', 
           'latestJig', 'latestUndercoatData', 'latestTopcoatData',
           'averagePersonnelCount', 'latestLineRatio', 'averageRPM')
  )
);
```

**효과**: 네트워크 전송량 50-70% 감소

### 4. 서버 사이드 검색 및 필터링

**목적**: 클라이언트 사이드 필터링 대신 Firestore 쿼리 활용

**구현**:

- 검색어를 Firestore 쿼리로 변환
- `where` 절과 `orderBy`를 활용한 서버 사이드 정렬
- 복합 인덱스 활용 (supplier, productName, partName 조합)

**효과**: 초기 로딩 후 검색 시 추가 네트워크 요청 없음

### 6. 로컬 캐싱 (IndexedDB)

**목적**: 오프라인 지원 및 반복 조회 시 네트워크 요청 제거

**구현**:

- IndexedDB에 `product-summary` 캐시 저장
- 캐시 유효 시간 설정 (예: 5분)
- 캐시 미스 시에만 Firestore 조회

**효과**: 반복 조회 시 즉시 응답 (0ms)

### 7. 부분 업데이트 최적화

**목적**: 변경된 필드만 업데이트하여 쓰기 비용 감소

**구현**:

- Cloud Functions에서 변경 전후 비교
- 변경된 필드만 `updateDoc`으로 업데이트
- 집계 필드(averagePersonnelCount 등)는 변경 시에만 재계산

**효과**: 쓰기 비용 60-80% 감소

### 8. 병렬 처리 최적화

**목적**: 여러 제품 업데이트를 동시에 처리

**구현**:

- Promise.all을 사용한 병렬 처리
- 최대 동시 처리 수 제한 (예: 10개)
- 실패한 항목은 재시도 큐에 추가

**효과**: 배치 업데이트 시간 70% 감소

### 9. 캐시 무효화 전략

**목적**: 불필요한 재계산 방지

**구현**:

- `lastUpdated` 필드로 변경 감지
- 변경사항이 집계에 영향을 주는지 확인
- 영향 없는 변경(예: 메모만 변경)은 스킵

**효과**: 불필요한 재계산 40-50% 감소

### 10. 실시간 구독 최적화

**목적**: 필요한 데이터만 실시간 구독

**구현**:

- 검색어가 있을 때만 필터링된 쿼리 구독
- 페이지네이션된 데이터만 구독
- 변경사항이 있을 때만 업데이트

**효과**: 실시간 업데이트 오버헤드 50% 감소

## 성능 개선 종합 효과

### 현재 방식

- 초기 로딩: 2-5초
- 검색: 클라이언트 필터링 (즉시)
- 업데이트: 전체 재계산 (2-5초)
- 네트워크: 4000개 문서 (약 2-5MB)

### 기본 캐시 방식

- 초기 로딩: 0.5-1초
- 검색: 클라이언트 필터링 (즉시)
- 업데이트: 증분 업데이트 (0.5-1초)
- 네트워크: 100-500개 문서 (약 100-500KB)

### 최적화 적용 후

- 초기 로딩: 0.5-1초 (캐시 컬렉션 조회)
- 검색: 서버 사이드 (0.1-0.3초)
- 업데이트: 증분 업데이트 (0.1-0.3초)
- 네트워크: 100-500개 문서 + 필드 선택 (약 100-500KB)
- 반복 조회: 0ms (로컬 캐시)

## 주의사항

1. 초기 마이그레이션: 기존 데이터로 캐시 컬렉션 초기 구축 필요
2. 데이터 정합성: Cloud Functions 실패 시 수동 재계산 필요
3. 비용: Cloud Functions 호출 비용 증가 (하지만 읽기 비용 대폭 감소)
4. 복잡도: 증분 업데이트 로직이 복잡해질 수 있음
5. 테스트: 각 최적화 단계별 충분한 테스트 필요
